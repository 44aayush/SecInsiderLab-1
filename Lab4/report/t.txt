Abstract
In the fourth lab of the Security Insider Lab, we build a complete real-time DDoS defense cycle with
eBPF/XDP in which the classifier and the filter run inside the Linux kernel. One XDP program
captures packets at the network driver hook, computes ten forward-direction flow features per flow in a
kernel map, classifies the flow with a Decision Tree (depth 6) and an XGBoost model (20 trees, depth
4) stored in BPF maps, and drops all packets of a source that is classified as malicious. User space
only trains and exports the models, loads and configures the program, and displays results. On the
33,463 test flows of the CIC-IDS2017 Friday DDoS file, the integer models reach an F1 score of 0.9991
(Decision Tree, 4 false alarms, 32 missed attacks) and 0.9989 (XGBoost, 11 false alarms, 31 missed
attacks). Their verdicts agree with the floating-point models on all test flows, and the kernel code
reproduces the Python integer evaluator exactly on 1,024 test vectors. In a Docker topology with an
inline IDS gateway in front of Nginx and Apache, normal client traffic produced no malicious verdict
and no drop, and a stub model that always answers malicious showed the filter dropping 55 packets
of the normal client. Without attack tools, 60 dataset flows replayed through the attached kernel
program were handled correctly: all 30 DDoS flows were classified malicious and blocked, and none of
the 30 benign flows. We also configured xdp-filter and xdpdump (Task 1), built a web interface (Task
3) and containerized Nginx, Apache and a pinging container (Task 4). The models are essentially a
payload-size rule, which we discuss together with the other limits of the in-kernel design.

1 Introduction
In the fourth lab of the Security Insider Lab, we move the DDoS detection of Lab 3 from user space
into the Linux kernel. A flow classifier that runs in a Python process sees a packet only after the kernel
has received, queued and copied it. The eXpress Data Path (XDP) [Høi+18] runs a small, verified
eBPF program at the earliest point of the receive path, before the network stack allocates its packet
structures. A program at this hook can read a packet, update state in kernel maps and drop the packet
at once. The lab has four tasks:
  1. Task 1: configure the xdp-tools collection [XDP] and run example commands of xdp-filter and
     xdpdump.
  2. Task 2: build a real-time cycle: capture packets, compute flow features, classify each flow, and
     filter it. We chose the best case of the task sheet: the classifier and the filter both run in the
     kernel, inside one XDP program. User space only loads the models, configures the program and
     displays results.
  3. Task 3: build a web interface with an interface selector, a timespan, a start button and a table
     with the algorithm output.
  4. Task 4: run Nginx, Apache and a pinging container in Docker and check that they can
     communicate.
Scope and rules. The task sheet forbids attacking tools in the real-time test. We therefore show
the filter without any attack tool: with normal client traffic, with a stub model that always answers
“malicious”, and by replaying flows of the dataset through the attached kernel program (Section 3.9).
The classifier is a Decision Tree (DT), an XGBoost model (XGB), or both (--model DT|XGB|ALL). With
ALL, both models run in the kernel and a flow counts as malicious only if they agree.

Data. We use the Friday-afternoon DDoS file of CIC-IDS2017 [SLG18] with the cleaning and the
70/15/15 stratified split of Lab 3: 225,745 raw flows become 223,082 after removing 34 rows with
infinite or missing values and 2,629 duplicates, and the split gives 156,157 training, 33,462 validation
and 33,463 test flows (test: 19,202 DDoS, 14,261 benign; outputs/metrics/preprocess_summary.json).
Labels are BENIGN = 0 and DDoS = 1.
Structure. Chapter 2 covers Task 1. Chapter 3 is the core of the report: architecture, kernel features,
integer models, training, verification, the live cycle and the dataset replay. Chapters 4 and 5 cover
the interface and Docker. Chapter 6 discusses limits, Chapter 7 concludes, and Appendix A lists
the commands to reproduce everything. Every number comes from files under outputs/ or from the
metadata of models/kernel_model.json; the file is named in the caption or the text.

3.1 Architecture
The cycle has four steps: capture, flowmeter, classification and filtration. In our best-case design all
four run in one XDP program, xdp_ids (xdp/lab4_xdp.bpf.c), attached to the interface ext0 of an IDS
container that acts as an inline gateway between a client and two web servers (Figure 3.1; the Docker
setup is in Chapter 5).

  1. Capture. The program sees every frame of ext0 before the IP stack. IPv4 TCP and UDP packets
     are parsed with bounds checks; ARP, IPv6, ICMP, fragments, VLAN frames and malformed
     packets pass untouched and are counted.
  2. Blocklist. If the source address is in the blocklist map and the entry has not expired, the
     packet is dropped. Expired entries are deleted on the next packet of that source.
  3. Flowmeter. A least-recently-used hash map flows keeps one record per 5-tuple with packet and
     byte counters, the packet length extremes and the inter-arrival times.
  4. Classification. At certain packets of a flow (below) the program computes the ten features of
     Section 3.2 and walks the integer trees stored in the maps nodes and roots.
  5. Filtration. A malicious verdict writes the source into the blocklist for --block-seconds (default
     60 s) and drops the packet. All internal errors fail open: the packet passes.

3.2 Kernel features
XDP runs on ingress only. In our topology the program therefore sees the client-to-server packets
of a flow, the forward direction, and never the replies. CICFlowMeter, which produced the dataset,
also computes backward and bidirectional features (flow duration, bytes per second, backward packet
lengths). Computing them differently in the kernel would silently change their meaning, so we use only
ten forward-direction features that the kernel computes exactly with integer arithmetic (Table 3.1).
The payload length is the IPv4 total length minus the IP and the TCP or UDP header, never the
frame length, so Ethernet padding is not counted. We left out two features that score highly in Lab 2
and Lab 3 but are shortcuts: the destination port (nearly all DDoS flows of the file go to port 80,
which is exactly the port of our demo web servers, so a port-based model would flag normal demo
traffic) and Init_Win_bytes_forward (a fingerprint of the 2017 attack hosts). We also left out the
standard-deviation features, which need an integer square root and CICFlowMeter’s conventions,
and the header-length features with known CICFlowMeter quirks. The cost in accuracy is small
(Section 3.6).

     3.3 Integer decision trees
     eBPF has no floating-point arithmetic. Trees are invariant to feature scaling, so we train on the raw
     feature values (no scaler) and convert the thresholds. Features and thresholds are integers in kernel
     units: xint = bx · sc with the scale s of Table 3.1. A sklearn tree goes left if x ≤ t, so T = bt · sc.
     XGBoost goes left if x < t for a float32 threshold t, so T = dt · se − 1. In both cases the kernel rule is
     the same: left iff xint ≤ T .
     A Decision Tree leaf is class 1 if P (DDoS) > 0.5. An XGBoost leaf value is stored as a fixed-point
     integer round(leaf · 216 ); the base score becomes a margin round(logit(b) · 216 ). The verdict is malicious
     if the margin sum is positive (an exact zero is normal, matching the rule score > 0.5). The exported
     model has 387 nodes in total (models/kernel_model.json, key meta). Each node is 24 bytes (struct
     tree_node); the maps hold up to 8,192 nodes and 64 trees. The decision tree root is roots[0], the
     XGBoost trees are roots[1..20].

     3.4 The XDP program
     Listing 3.1 is the core of the classifier: a bounded loop that follows node indices in the nodes map. The
     constant bound lets the verifier prove termination, and each map lookup is checked for NULL. XGBoost
     sums its 20 trees with the helper bpf_loop, and classify (Listing 3.2) combines the verdicts: with ALL
     the flow is malicious only if both models say so, because the action is a drop and a false drop costs
     more than a missed detection in this demo.

     3.5 User space with bpftool
     User space contains no custom loader. The agent (script/agent.py) calls bpftool with an argument list
     (never through a shell): prog loadall with pinned maps, one batch file with all node, root and config
     updates, net attach xdpgeneric, JSON map dumps that carry BTF-formatted values, and prog run for
     tests. The program is attached only after the model and the configuration are in the maps, and always
     detached on exit. Once per second the agent dumps the flows and stats maps and prints one JSON
     line per classified flow. A per-interface file lock allows one capture per interface. The interface name is
     validated against /sys/class/net, the management interface is refused, and the timespan and model
     are range-checked. The command line is agent.py --iface ext0 --model {DT,XGB,ALL} --timespan S
     --block-seconds B --replay N (--replay 0 to 100, default 0).

3.7 Verification chain
We check three links. First, train.py compares the floating-point predictions with a Python integer
evaluator on all 33,463 test rows: the verdicts agree on 100 % of the rows for both models (0
mismatches), and the largest margin error of XGBoost is 4.5 · 10−5 (outputs/metrics/parity.json,
ac_pass true). Second, a second program classify_test in the same object evaluates 1,024 test
vectors in the kernel (BPF_PROG_TEST_RUN); the DT verdicts and XGB margins equal the Python
integer evaluator exactly. Third, kernel tests run the real program on crafted packets: flowmeter
counts, classification trigger, blocklist, block expiry, mode ALL needs both models, mode off, and the
pass-through of ARP, IPv6, ICMP, fragments, short packets, bad header lengths and VLAN frames.

decides what the trained model decides.

4 Task 3: Front-End Interface
The sample on the task sheet shows a dark page with a dropdown of local interfaces, a timespan field, a
Start Packet Capture button and a table called Algorithm Output with source and destination address
and port, a timestamp and the result (Normal or Malicious). We built the same page (web/index.html,

4.1 Controls and API
  • Available Local Interfaces: filled from GET /api/interfaces. The management interface mgmt0
    is hidden, so the page cannot attach a program to the interface that carries its own traffic. The
    default is ext0.
  • Enter Timespan: seconds, 1 to 3600.
  • Model: DT, XGB or ALL (we added this dropdown to the sample).
  • Replay dataset flows: number of test-split flows replayed through the kernel program at
    random times over the first 80 % of the capture, interleaved with live flows (default 20, 0 to 100;
    Section 3.9).
  • Start Packet Capture / Stop: POST /api/start answers 202, 400 for invalid input or 409 if a
    capture is already running on the interface; POST /api/stop ends it.
  • Status line and table: the page polls GET /api/flows. The status line shows the remaining
    time and the counters (packets, dropped, classified, malicious, blocks). Malicious rows are red.
    The Models column shows the verdict of each model.
The server validates every field (interface, timespan, model, a request body of at most 4 KB). It listens
only on the management address 172.28.0.2:8080, so the browser on the host can reach it, but the
client behind the XDP hook cannot, and its own polling never crosses ext0.

6 Discussion
What the results show. A decision tree and a 20-tree XGBoost model fit into one XDP program of
5,664 translated bytes, and the kernel reproduces the Python integer models exactly. A classification
costs between about 120 ns (DT) and 366 ns (XGB); mode ALL runs both models and costs about
their sum (542 ns) in the measurement of Table 3.5. The F1 scores of 0.9991 and 0.9989 are within
about 0.001 of the models of Lab 3 that use 59 features, although the kernel models use ten.
The model is a payload-size rule. Two features, the largest forward payload and the total forward
payload, carry about 99 % of the importance (Table 3.4). The Friday DDoS flows are an HTTP flood
with a characteristic request size, and the trees learned that size. The high F1 therefore says that this
attack is easy to separate by request size within the test split. It says little about other attacks or
other networks, and the live demo traffic (small wget requests) happens to fall on the normal side.
We did not tune the thresholds for the demo. Had normal flows come out malicious, we would have
reported it instead of changing features.
Ingress only. XDP runs on receive, so the program sees only the forward direction. Backward and
bidirectional features (flow duration, bytes per second, backward packet lengths) are absent, because
computing them differently from CICFlowMeter would change their meaning (Section 3.2).
Partial flows. CICFlowMeter rows describe completed flows. The kernel classifies at FIN or RST and
at power-of-two packet counts from 8 on, so a flow with fewer than 8 packets and no FIN or RST (for
example a short UDP exchange) is never classified, and a source can send many such flows unblocked.
A timer-based idle expiry would close this gap and is out of scope. A reused 5-tuple continues the old
flow entry, which is rare with ephemeral ports. Flow counters are not atomic across CPUs, which is
accepted at demo rates.
No attack tools. The task sheet forbids attacking tools. The filter is therefore shown with a stub
model on normal traffic and with the dataset replay. The replay rebuilds the forward packets of dataset
flows, but the inter-arrival times are not reproduced (Section 3.9), and it uses flows of the test split, so




                                                    19
it does not measure robustness against a new attack. Classifier performance on live malicious traffic
was not checked, as the sheet allows.
Other limits. Only IPv4 TCP and UDP are inspected; everything else passes. The program runs
in generic (skb) mode, because native mode on veth needs extra setup. The privileged container is
root-equivalent. The consensus rule of ALL drops fewer flows than either model alone, so a flow that
only one model flags is passed. Remedies such as multi-day training data or more features were not
part of this lab.
7 Conclusion
We built the best case of the real-time cycle: one XDP program that captures packets, keeps per-flow
features in a kernel map, classifies flows with a Decision Tree and an XGBoost model stored in BPF
maps, and drops all traffic of a source that is classified as malicious. User space only trains, exports
and configures. The integer models match the floating-point models on all 33,463 test flows and the
kernel matches the Python evaluator exactly on 1,024 vectors; the test F1 is 0.9991 (DT) and 0.9989
(XGB). In the Docker gateway topology, normal traffic caused no drop, a stub model showed the filter
blocking the client, and 60 replayed dataset flows were handled correctly, all 30 DDoS flows blocked
and none of the 30 benign flows. Task 1 documented xdp-filter and xdpdump in a sandbox, Task 3
provides the interface, and Task 4 shows that Nginx, Apache and the pinger communicate. The main
limit is the narrow basis of the classifier: it is essentially a request-size rule from one attack file.
